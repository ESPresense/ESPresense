# Reference detector benchmark

This is a research build for the fixed **Family** and **Master** nodes. It does not deliver an occupancy feature. Compare the unchanged upstream ESPectre Lightweight and High Accuracy detectors with the earlier sparse-stream approximation, then evaluate whether motion plus BLE improves occupancy over BLE alone.

## Source and build

`tools/prepare_csi_reference.py` fetches upstream commit `3edc7bdb4262e01b868c3d589fea59cfd0e8f555`, preserves its license notices, and records the archive hash. The SDK sources, capture, normalization, model weights, calibration, and admission policy are unchanged. The `CSI Reference Benchmark` workflow builds **only** `esp32c3-csiref` under IDF **5.5.6**. Existing firmware variants keep IDF 5.4.4; their CSI implementation and dependencies are unchanged. Image size must fit the existing 1,966,080-byte OTA slot.

Build locally with `python3 tools/prepare_csi_reference.py`, the IDF 5.5.6 environment, and `./build.sh esp32c3-csiref`.

The integration retains ESPresense networking, BLE scanning, configured plug GPIOs, SPIFFS settings, and OTA. It uses the full upstream SDK rather than a locally fitted copy of two features. The SDK's PING generator is configured for 100 requests/s to the associated WiFi gateway, keeps WiFi power save off, and controls its radio policy, including its WiFi coexistence preference. `generated` counts successful generator sends; `tx` and `rx` count all station traffic and cannot establish the achieved ping/reply rate. All of those costs belong to the reference result. Association, gateway identity, actual CSI rates, slot coverage, and BLE counters must be recorded rather than inferred from the requested packet rate.

## Bounded operation

The benchmark is off by default. `/wifi/hardware` exposes `csi_reference_mode` (0 off, 1 Lightweight, 2 High Accuracy), `csi_reference_arm` (one-shot arming, default off), and `csi_reference_until` (absolute UTC Unix seconds). They take effect after reboot. The reference cannot arm before NTP establishes a valid clock or with an expired deadline or a deadline more than 48 hours away. Before starting the SDK it must successfully persist arm=false, so a crash or reboot cannot restart active sensing. The configured mode remains as the last requested detector; read live `CSIREF` output to determine actual runtime activity. Once armed, a monotonic timeout also bounds the trial if wall time changes. Expiry restarts to restore ordinary radio policy; it requires no further flash write. Set the first pilot deadline about 15 minutes ahead, not a day ahead.

The first hardware pilot exposed malformed JSON from ESP-IDF nano printf, which does not implement `%lld`/`%llu`. Reference telemetry therefore converts 64-bit integers into exact decimal strings before `%s` formatting. Host boundary tests cover microsecond wrap, UTC, and full-width counters. Pipeline 2005 produced no usable measurement; it is not evidence about detector accuracy or BLE cost. The unchanged SDK sources and weights are independent of this integration logger fix.

Pipeline 2010 completed all four controlled phases but exposed a processing bottleneck: station RX reached about 100/s while the SDK's eight-frame queue lost thousands of CSI frames, slot coverage averaged about 13%, and neither detector became ready. That station counter did not isolate ping replies; their achieved rate was unverified. This was an integration/acquisition failure, not detector-accuracy evidence. Its summaries and raw captures are preserved privately.

The reference now gives the SDK a single worker using the pinned native frontend's scheduling defaults: 8 KiB stack, priority 5, and a 10 ms loop delay. The ordinary ESPresense loop can yield per BLE fingerprint and block on serial/MQTT; it must not pace the CSI consumer. A one-element value mailbox separates SDK processing from log formatting. `report_seq` and `telemetry_overwrites` expose replaced log snapshots separately from SDK `queue_drops`; `worker_loops`, `loop_gap_max_us`, and `worker_stack_free` record scheduling and stack evidence. The extra task and memory cost belong to the measured result. Capture, admission, calibration, model weights and hit filtering remain unchanged. A new controlled pilot must verify the fix; source inspection alone does not establish valid input or stability.

The worker repeat (2012) reduced Lightweight queue loss to two frames and increased mean slot coverage to 41%, but readiness remained zero. High Accuracy was not measured because its initial post-boot HTTP request timed out. The bench client retries bounded transport startup failures while still rejecting an unexpected build immediately, and saves each completed phase before attempting the next.

Pilot 2014 reached Lightweight again, with no CSI queue drops but insufficient window coverage. A serial JSON decode error then stopped High Accuracy before the controls or safety probes ran; the concurrent TCP capture had no malformed reference records. The serial reader now accumulates timeout fragments until a newline, with an 8 KiB bound. A timed-out partial read must not be parsed as a complete JSON record. This is a transport correction, not a relaxation of readiness or input validation.

Pilot 2016 completed the off baseline but hit another serial JSON error before completing Lightweight. Fragment buffering alone did not resolve transport loss. The reader now drains serial continuously during HTTP setup into a bounded queue; overflow or malformed records still invalidate the trial. This addresses a possible UART-buffer overrun during blocking HTTP calls and needs a controlled repeat to establish the cause. A lost restart response is accepted only after a fresh serial boot and exact firmware identity; the client never repeats a possibly delivered reboot. Cleanup verifies the persisted off/arm/deadline/scanning settings and live detector-off output, while retaining the original trial error if cleanup also fails.

Pilot 2018 preserved five completed phases without another serial parse error. Both BLE-on detectors had zero ready time, about 64 successful generator sends/s, and about 37% slot coverage during observed telemetry; gaps reduced total-time coverage to about 26%. Lightweight with scanning off achieved 99 sends/s, 84% coverage and 98.6% ready time. This establishes a coexistence/acquisition problem, not occupancy accuracy or an isolated RF cause: disabling scanning also removes fingerprint/reporting workload. High Accuracy's scan-off control and both safety probes were not completed because its hardware-settings GET timed out. Cleanup was verified. Read-only hardware requests now use bounded transport retries; wrong settings still fail. `--phase-start 5` resumes the final control and safety checks without repeating or replacing the preserved phases. In Crow, pass `--var REFERENCE_PHASE_START=5` when creating the manual pipeline. Partial runs explicitly cannot pass the house gate.

`csi_reference_ble_scan` defaults to true. A false value is an explicit diagnostic control: the BLE stack stays initialized, but the scan task does not start or automatically restart scanning. The manual bench runs the normal four phases with scanning enabled first, then both detectors with scanning disabled. The latter must receive zero scan callbacks and cannot establish BLE coexistence, BLE cost, or room occupancy usefulness. Extra CSI rejection/admission counters identify driver/filter/timing losses. Bench cleanup requests scanning=true and reboots; verify this restoration after a failed run. No house trial is authorized by a control-only pass.

The same device lock covers one-shot and persistent-expiry probes. A one-shot probe observes active sensing, reboots before the saved deadline, then requires detector-off output with the original deadline and a consumed arm. An expiry probe leaves the active runtime alone through a 90-second deadline, requires a software-reset boot into detector-off, and watches for repeated reboot or resumed sensing. These are safety checks; their success does not replace the input/readiness gate.

Pilot 2020 resumed only the final High Accuracy control and safety checks. With scanning off it achieved 97 sends/s, 82% slot coverage and 100% ready time; it still recorded some CSI queue loss. The one-shot reboot, persistent expiry and verified cleanup checks passed. Together with 2018, this establishes that both detectors can obtain ready input on this fixture with scanning off, while the tested BLE-on PING configuration fails. A partial control run does not authorize a house trial.

Pilot 2021 supplied external traffic at 100.001 successful sends/s with no sender errors or missed deadlines. With BLE scanning enabled, Lightweight accepted about 97 CSI frames/s but admitted only 48/s; observed slot coverage was 48% and ready time remained zero. A serial JSON error stopped High Accuracy before it completed; cleanup was verified. External pacing alone did not resolve the high-load input problem. Malformed telemetry now faults the entire phase and makes the surrounding interval unknown, while allowing subsequent diagnostic phases to finish. Error records contain a digest and a redacted structural pattern, never raw interleaved names or identifiers. Reboots, wrong sources, wrong scan conditions and counter resets remain fatal; transport faults cannot pass the input gate.

`REFERENCE_BLE_POOL=64` is a separate workload diagnostic at the same requested 40 rotations/s. The default remains the original 1,024 identities, whose negative results stay preserved. A read-only snapshot found 68 cached fingerprints in Family and 69 in Master; this motivates testing fewer identities but does not establish equal radio load or room conditions. Run PING first so the detector can be evaluated without requiring an external sender. Record actual advertisement callbacks and the selected pool; a smaller-pool pass cannot establish performance under the original stress workload. SDK cadence, weights, calibration and admission remain unchanged.

Pilot 2022 completed all six measurement phases without malformed reference records. With 64 identities, both BLE-on detectors still had zero ready time, despite about 90 successful sends/s and 43% temporal slot coverage. Both scan-off controls passed. One-shot reboot passed, but a serial JSON error interrupted the persistent-expiry probe; cleanup was verified. Reducing identity/reporting load alone did not resolve acquisition.

The next build audits a possible dependency gap before another measurement. The SDK wraps its native Wi-Fi coexistence preference in a header-availability guard, while ESP-IDF's Wi-Fi component lists `esp_coex` as a private dependency. The reference-only wrapper forwards the unchanged upstream CMake and Kconfig and supplies `esp_coex` through the SDK's supported `ESPECTRE_SDK_ADDITIONAL_REQUIRES` hook, including IDF's separate requirements process. `REFERENCE_COEX_AUDIT=true` first compiles a comparison without that extra dependency, then recompiles with it. The audit records the SDK object's undefined-symbol reference to `esp_coex_preference_set`, header include visibility and software-coexistence configuration. Only the build with all three checks passes the pre-flash gate. The comparison establishes whether the call was previously omitted; until those object results exist, this remains a hypothesis. Compiled call presence does not by itself prove runtime API success or useful occupancy.

The separate `REFERENCE_TRAFFIC_SOURCE=external` acquisition diagnostic uses the SDK's existing `EXTERNAL_HOST` mode, with multicast disabled and the unchanged 100 pps temporal grid. PING remains the default. `csi_reference_external_host` is off by default, takes effect on reboot and is cleared by bench cleanup. Telemetry names the selected source; the client rejects a mismatched live source or scan condition. The external sender targets only the verified C3 fixture at `192.168.129.243:5555`, using the pinned SDK's four-byte marker. It sends no baseline traffic, starts after build/settings verification for each active phase, never catches up a missed deadline with a burst, and records successful sends, errors, skipped deadlines and pacing lateness. Its nonblocking thread has an independent hard expiry of at most 300 seconds and stops at context exit, including failures; safety probes share one bounded 300 second feed. Receiver counters still establish actual CSI input; a successful UDP send alone does not prove delivery. Both scan-on and scan-off phases remain separately identified. This diagnostic tests whether changing traffic ownership can supply valid input alongside BLE; it cannot replace the failed PING result or establish room accuracy. SDK sources, coefficients, thresholds and temporal admission remain unchanged.

Before flashing either node, save its current firmware identity, settings, board template, auto-update state, and a verified restoration artifact. Disable auto-update for the experiment. Only use an app image after checking target, size, successful bench boot, and OTA compatibility; never use a factory image over OTA. Do not restart a downloading node. Verify the post-flash boot log and `/json` build before arming. Retain a recorder through timeout and confirm disarm. Restore the original firmware/settings and auto-update state after the trial.

## Measurements and admission gate

Record the node TCP log on port 6053, polling `/json` for firmware identity and `/json/tele` for heap. `tools/csi_reference/collect.py` records both explicitly selected nodes in rotating gzip segments, records gaps and reconnects, writes a status heartbeat every five seconds, and stops at its absolute deadline or a 2 GB disk budget. A 90-second read-only pilot on both existing house builds verified real TCP/HTTP capture and deadline completion before any firmware change. `CSIREF` emits four snapshots/s with detector identity, monotonic and UTC time, readiness, score, threshold, calibration, accepted/admitted packet counts, temporal slot coverage, queue drops, traffic counters, heap, and a cumulative count of BLE advertisement callbacks received by the application before fingerprint filtering. Mode off still emits the BLE counter once per second. An unready interval is **unknown**, never an empty-room prediction. Calibration failures and queue loss stay in the report. The integration registers no HA motion sensor and drives no household automation.

First run a baseline/Lightweight/High Accuracy/baseline pilot with equal blocks on a fixed-load bench (`.woodpecker/csi-reference.yml`, manual event). The pipeline waits for a positive dongle-claim marker before measuring. Use cumulative **BLE advertisement callbacks delivered to the application** as the primary measurement, with counter resets and reboots treated as new epochs. This is not an over-the-air sniffer count. Serial New/Del fingerprint events remain a separate proxy. Neither `/json` nor `/json/tele` exports the advertisement counter in the existing firmware, so they cannot establish that rate. Measure heap and image budget, and record actual slot coverage: a requested 100 pps without sufficient valid CSI is an acquisition failure, not negative evidence about the detector.

After the pilot establishes stable, valid input, collect matched periods covering a normal day and night per room and detector. Rotate detector order across the rooms and repeat periods rather than confounding mode with one time of day. Evaluate the pre-trained upstream weights and calibration unchanged, without fitting on the evaluation period. Retain gaps and startup intervals in coverage statistics. Do not claim a controlled BLE result from ambient household traffic.

The TCP recorder renews a mirror after 30 seconds without a line. An ESP reset can otherwise leave a receive-only socket half open indefinitely. Each reconnect and gap remains in the capture; never infer detector availability across that gap.

`tools/csi_reference/collect_ble.py` separately subscribes to the existing MQTT broker and saves raw personal-tag reports across receivers for BLE-only replay. Install the pinned `requirements.txt` in an isolated environment. It publishes no application messages, retains only explicitly selected ID prefixes (default phone/watch/irk/keys/wallet), preserves the retained-message flag, and uses the same absolute deadline, rotating files, disk budget, and output lock as the TCP recorder. Retained startup messages are not live observations. Preserve the companion map, locator configuration, and calibration with the capture; tracker outputs cannot serve as their own reference labels.

## Map and reference labels

Use the companion's floor polygons and configured node coordinates, not node display names. Family and Master are the primary rooms; both use ESP32-C3 SwitchBot Plug Minis. The Master node is about 0.2 m from its shared bathroom wall; use the Master Bathroom, Closet, adjoining Office, and the floor below as interference checks. Family needs adjacent Kitchen and Laundry activity checked separately. The `laundry` node sits at `(4.3, 7.6, 1.4)` on the Downstairs Hall boundary, outside the Laundry polygon: earlier Laundry-only scoring is not a clean room-level validation. T-Embed moves and is excluded; Office's old M5StickC is not a primary validation node.

Verify the sensor histories and underlying definitions before assigning labels. Family PIR motion establishes positive motion evidence but PIR silence cannot establish absence. Family's aggregate occupancy and presence sensors have disagreed in earlier captures. Master currently exposes `master_bed_presence`, `master_presence` (Aqara FP2), and aggregate `master_occupancy`; inspect their coverage and dependencies rather than treating their names or one current state as truth. Do not use BLE-derived reference labels to validate BLE fusion. Keep uncertain and unavailable intervals explicitly unlabelled.

## Product evidence required

Use the user's existing room `_occupancy` entities as the operational reference after tracing their input definitions for BLE dependence. Save the actual HA histories, including expiry attributes and input-health flags. Aggregate occupancy can retain a person after raw motion clears; preserve that retention policy when measuring departure latency. A repository snapshot of the template can differ from deployed timing, so cross-check it against the live output and do not reconstruct reference labels from an older source file.

Report motion detection and occupancy as different outcomes. Score arrivals, retained occupancy while still, departures, a person without a tracked device, and activity in neighboring rooms. Compare CSI plus BLE with BLE alone on the same evaluation intervals. Report per-room recall, precision, arrival/departure latency, false occupancy episodes/hour, false occupancy duration, missed occupancy duration, room flapping, and the fraction of time with valid labels and ready input. AUC and false-positive windows/hour alone cannot establish useful occupancy. Preserve a reproducible negative result if neither detector helps; green CI or a merge does not satisfy the outcome.
